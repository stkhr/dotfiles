# 運用点検 チェックリスト

外部に公開しているアプリ・利用している外部サービス・保有データを、稼働中の状態として点検するための質問集。
コードの境界レビュー([boundary-review.md](boundary-review.md))では見えない「今どう動いているか」を確認する。

出典: IPA・JPCERT/CC の注意喚起(2026-10)と [ipa-public-app-security-check](https://github.com/fado-dev/ipa-public-app-security-check)(MIT)を要約・再構成。

## 点検の前提

- 照合する IOC(不審な IP・User-Agent)は JPCERT/CC・IPA の最新の注意喚起から取り、このファイルに固定しない
- IOC との一致は調査の起点であり、単独で侵害と結論づけない。アクセス先・時間帯・その後の挙動と合わせて評価する
- 本番のログ・設定の確認は読み取りに留める。侵害の兆候が見つかったら [incident-response.md](incident-response.md) に移る
- 対応体制(連絡網・封じ込め権限・バックアップ等)は [incident-response.md](incident-response.md) の「平時の準備」で確認する

## 1. 公開資産の棚卸し

| 確認事項 | 見る場所 |
| --- | --- |
| 外部から到達できるアプリ・エンドポイントをすべて列挙したか | IaC(Terraform・k8s manifest・serverless 定義)、DNS、LB・CDN・リバースプロキシの設定、ルーティング定義 |
| 管理画面・社内ツール・BI・バッチ用エンドポイント・Webhook 受信口・ヘルスチェック・デバッグ機能など、公開しているつもりのないものが含まれていないか | ルーティング定義、`admin` `internal` `debug` `actuator` `swagger` `graphql` 等のパス |
| モバイルアプリが呼ぶ API に、画面から呼ばれない内部 API・管理 API が含まれていないか | API 仕様、アプリのネットワーク定義 |
| アプリごとにログの所在・保持期間・確認できる人を即答できるか | ヒアリング |

棚卸しの結果は「名称 / 公開 URL・ポート / 用途 / 想定利用者 / 認証方式 / ログの所在と保持期間 / 担当」の表にまとめる。

## 2. ログに残る侵害の兆候

直近 1 か月から見始め、兆候があれば 3 か月に広げる。エラー量・4xx/5xx 率・時間帯・送信元の国を平時と比べる。

| 兆候 | 想定される手口 |
| --- | --- |
| `.env` `.git/` `config.*` `*.bak` `*.sql` `*.zip` `backup*` へのアクセス試行 | 設定ファイル・バックアップの探索 |
| 4xx が続いた直後に 200 が返っているパス | 探索の成功 |
| 認証ヘッダー欠落・不正形式トークンでの 401/403/400 の連続 | 認証処理の応答差の探索 |
| クエリ・ボディに `$ne` `$gt` `$regex` `$where` や `UNION` `information_schema` | NoSQL / SQL インジェクション |
| 見覚えのない `.jsp` 等へのリクエスト、`cmd=` `exec=` `command=` パラメータ、AP サーバ上の新しい `.war` `.jsp` | Web シェルの設置 |
| 画面操作では呼ばれないエンドポイントへの直接アクセス、同一送信元からの短時間の大量リクエスト | API の直接悪用 |
| ログイン・パスワードリセット・SMS 送信・検索の回数の急増 | 総当たり、リスト型攻撃、データ収集 |
| 権限変更・アカウント作成の操作 | 不正アカウントの作成、権限昇格 |
| 発行元と利用元が一致しない API キーの利用 | 他所で窃取されたキーの利用 |
| BI ツールでの通常業務と異なるクエリ(システムテーブル参照、大量行の取得) | BI 経由のデータ持ち出し |

AWS 上のログ(CloudTrail・ALB アクセスログ・CloudWatch Logs)を調べる時は `aws-investigation` スキルに従う。

## 3. アカウント・キーの棚卸し

- 作成した覚えのないアカウントがないか
- 退職・異動・削除済みのはずのアカウントが有効になっていないか
- 管理者権限の保有者が最小限で、全員把握されているか
- 長期未使用のアカウントが無効化されているか
- API キー・トークンの発行日・有効期限・用途・発行先が一覧化されているか

## 4. 利用している外部サービス

クラウド・SaaS・VPN・CI/CD・監視ツールを組織全体で洗い出し、サービスごとに確認する:

- ログの保持期間と、提供者側・利用者側でそれぞれ確認できる範囲。誰がどう確認するか
- ログイン失敗数、ログイン元 IP・時間帯が平時と比べて異常でないか
- 3 と同じ観点でのアカウントの棚卸しと、作成・変更履歴の確認
- MFA 未設定のアカウント(特に特権)がないか
- OAuth アプリ・API 連携・サービスアカウントが棚卸しされ、不要なものが削除されているか
- クラウドの IAM キー・ロールが最小権限で、未使用キーがないか
- 監査ログ(CloudTrail 等)が有効で、別アカウント・別ストレージへの転送で改ざんを防いでいるか

## 5. 保有データ

「不要な情報は持たない」を前提に確認する:

- 個人情報・機微情報を含むデータストアの一覧(場所、件数規模、項目、保持目的、保持期限)があるか
- 保持期限を過ぎた・利用目的を終えたデータが残っていないか
- 本番データのコピー(ステージング、ログ、バックアップ、BI の抽出先、手元の端末)が把握されているか
- 保存時に暗号化され、データアクセスのログが取得・保持されているか
- 漏えい時に影響範囲(件数・項目・対象者)を即答できるか

## 6. 強化策の観点

異常がなくても検討する。優先度は悪用時の影響と実施コストで付ける:

- 公開範囲の縮小(不要な管理機能の非公開化、IP・地域制限)
- 特権アカウントと外部サービスの MFA 必須化
- ログイン・パスワードリセット・SMS 送信・検索の個別レート制限
- 非公開 API を含め、許可した利用者と HTTP メソッドだけを受け付ける
- API トークンの最小権限・有効期限・即時失効手順
- ログの保持期間を最低 3 か月、できれば 1 年以上にし、改ざんできない場所へ転送する
- Web サーバ侵害後の横展開の抑止(ネットワーク分離、認証情報の分離)
- 不要なデータの削除と、残すデータの暗号化
- 入退社・異動時にアカウントを即時反映する棚卸しの運用
