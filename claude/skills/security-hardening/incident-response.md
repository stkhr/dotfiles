# インシデント対応 チェックリスト

侵害の疑いがある時の初動と、平時の準備を確認するための質問集。
流れは JPCERT/CC インシデントハンドリングマニュアルと NIST SP 800-61 Rev.2 のライフサイクルに沿う。

出典: IPA・JPCERT/CC の注意喚起(2026-10)と [ipa-public-app-security-check](https://github.com/fado-dev/ipa-public-app-security-check)(Copyright (c) 2026 fado-dev, MIT License)を要約・再構成。

## 最初に守ること

- 証拠保全が済むまで、対象のログ削除・ローテーション・再起動・再構築・ファイルの削除や上書きをしない
- Web シェルや不審ファイルは実行も削除もせず、隔離した保管先へハッシュ付きでコピーする
- 封じ込め・根絶・復旧の操作は、手順と影響を示して担当者の承認を得てから実行する
- 侵害の疑いがある時点でセキュリティインシデントとして扱い、専門ベンダー(フォレンジック)への調査依頼を推奨する
- 調査コマンドの実行も対象環境のログに残るので、実行前に担当者へ伝える
- 攻撃者への接触、身代金の支払い判断、公表の文面は技術者だけで決めず、経営層・法務・警察に相談するよう促す
- 報告義務の期限・要否は業種・契約で変わる。下表は目安として扱い、最終判断は法務に確認する

## フェーズ別チェック

レポートとは別に、タイムラインとフェーズごとの対応状況(完了・未完了・次のアクション)を更新し続ける。

### 1. 検知・トリアージ

- 何を・いつ・どこで・どの手段で検知したかを記録し、タイムラインを始める
- 対応責任者を決め、侵害された可能性のないチャネルで第一報を出す
- 影響を受けうるシステム・アカウント・データを暫定で特定し、深刻度とエスカレーション先を決める
- 攻撃が継続中か判断する。継続中なら封じ込めを優先する
- 対応に使う端末・アカウント自体が侵害されていないか確認する
- 影響範囲の特定と報告要否の判断を、封じ込めと並行して始める。速報は復旧を待たない

### 2. 証拠保全

- 対象期間のログ(Web・AP・DB・認証・クラウド監査・WAF/CDN・IdP)を別の場所に書き出し、ローテーションによる消失を止める
- 書き出したファイルの SHA-256・取得日時・取得者と、誰がどこへ移したかを記録する
- 侵害が疑われるホストは、再起動・再構築の前に揮発性の高い順(メモリダンプ → スナップショット・ディスクイメージ)で取得する
- SaaS 側のログは保持期間が短いことがあるので、早めにエクスポートを依頼する

### 3. 封じ込め

- 攻撃者に気づかれて証拠を消されないよう、封じ込めの順序と同時に実行する範囲を先に決める
- 侵害経路(該当機能・エンドポイント・ホスト)を遮断または公開停止する。侵害ホストはネットワークから隔離し、電源は切らない
- 攻撃元 IP の遮断・WAF ルールは一時対応として扱う(IP は変わる)
- 侵害された・疑わしいアカウントを無効化し、セッションを失効させる
- 侵害されたシステムが持つ全シークレット(DB パスワード、API キー、署名鍵、OAuth クライアントシークレット、SSH 鍵)をローテーションする
- 同じ認証情報を使う他システムを特定し、横展開の有無を確認する
- 封じ込め後も、別経路・別アカウントからの活動がないか監視する

### 4. 根絶

- 侵入経路(脆弱性・設定不備・漏えいした認証情報)を特定して塞ぐ
- Web シェル、不正アカウント、不正な API キー・OAuth 連携、永続化の痕跡(cron、systemd、SSH authorized_keys、sudoers、新規ユーザー、不審プロセス)を除去する
- 侵害されたホストは修正で済ませず、クリーンなイメージから再構築する
- 同じ脆弱性・設定不備が他のシステムにないか確認する
- バックアップ自体が侵害・暗号化されていないか確認する

### 5. 復旧

- 修正・設定変更・シークレットのローテーションが終わってから、クリーンなバックアップか再構築した環境で復旧する
- 公開範囲を段階的に戻し、監視を強めた確認期間(2 週間〜1 か月が目安)を置く

### 6. 影響範囲の特定

- アクセス・持ち出しの可能性があるデータの種類・項目・件数・対象者と、攻撃者がアクセスできた期間(初回侵入から封じ込めまで)
- 持ち出しの証跡(大量レスポンス、外部への転送、DB ダンプ)
- 二次被害(なりすまし、不正利用、フィッシング、他サービスへのリスト型攻撃)の可能性
- 取引先・委託元のデータが含まれるか
- 特定できない場合は、最大の範囲を前提に報告・通知する

### 7. 報告・通知

- 下表の報告先ごとに要否と期限を決め、本人通知・公表・問い合わせ窓口を用意する
- 公表の要否・時期・文面は経営層・法務・広報で決める
- 脅迫を受けたら攻撃者と接触せず、警察に相談する

### 8. 事後対応

- 根本原因(技術・運用・組織)を分析し、再発防止策に期限と担当を付ける
- 検知までと封じ込めまでの時間を含めて振り返り、平時の準備に反映する
- IOC(IP、User-Agent、ファイルハッシュ、手口)を JPCERT/CC 等に共有する
- 認可マトリクス・監査条件など、SKILL.md の不変条件を見直す

## 報告・通知先(日本国内の目安)

| 報告が必要になる場面 | 報告先 | 期限の目安 |
| --- | --- | --- |
| 個人データの漏えい等(おそれを含む)が、要配慮個人情報・財産的被害のおそれ・不正目的によるおそれ・1,000 人超のいずれかに当たる | 個人情報保護委員会と本人 | 委員会への速報は概ね 3〜5 日以内、確報は 30 日以内(不正目的によるおそれは 60 日以内)。本人へは速やかに通知し、困難なら公表等で代替 |
| 業法で報告義務がある | 所管官庁 | 業法・ガイドラインによる |
| 不正アクセス・脅迫を受けた | 都道府県警察のサイバー犯罪相談窓口 | 速やかに |
| 手口や IOC を共有・調整したい | JPCERT/CC・IPA | 任意 |
| 受託データが含まれる、契約で報告義務がある | 取引先・委託元 | 契約による |
| 上場企業で投資判断に影響する | 証券取引所 | 適時開示 |
| カード情報が漏えいした | カードブランド・アクワイアラ | 契約による(PCI DSS) |

## タイムラインの記録様式

```markdown
| 日時 (JST) | 事象 / 行動 | 実施者 | 根拠・証跡 |
| --- | --- | --- | --- |
| YYYY-MM-DD hh:mm | [検知した事象、または実施した対応] | [担当] | [ログ名・チケット・チャネルの記録] |
```

- 事実と推測を分けて書く。推測は「〜の可能性」と書く
- 時刻の出典(ログの時刻かシステム時計か)とタイムゾーンを書く
- 判断ごとに根拠と判断者を残す

## 平時の準備

異常がなくても、侵害時に動けるかを確認する:

| 領域 | 確認事項 |
| --- | --- |
| 体制 | 対応責任者と技術責任者、役割分担(指揮・調査・封じ込め・記録・広報・法務)、夜間休日を含む連絡網、侵害されたシステムと独立した連絡チャネル、専門ベンダーへの依頼手順 |
| 検知 | 監視・アラートの受け手、インシデントと判定する基準、深刻度の分類とエスカレーション先、注意喚起・IOC を定期的に照合する運用 |
| 証拠保全 | 各システムのログの所在・保持期間・書き出し方法、改ざんできない保管先、スナップショットの取得手順、全システムの時刻同期 |
| 封じ込め・復旧 | 公開停止・IP 遮断・アカウント無効化・トークン失効を誰が・どの権限で・何分で実行できるか、全シークレットの一覧とローテーション手順、隔離された複数世代のバックアップと復元テストの実績、IaC 等からの再構築手順 |
| 報告 | 報告先と期限の一覧、報告様式・顧客通知文・公表文の雛形、問い合わせ窓口の立ち上げ手順、契約上の報告義務 |
| 脅迫・二次被害 | 脅迫を受けた時の方針(支払わない、接触しない、警察に相談)、顧客に MFA 設定・パスワード変更を呼びかける文面 |
| 訓練 | 年 1 回以上の机上演習、過去のインシデントの振り返りの反映 |
